* **hono-credit: DB-agnostic credit management via CreditStore adapter interface**: hono-usage-limiter is Hono-focused but database-agnostic — users implement \`UsageStore\` (5 methods: \`getBucket\`, \`createBucket\`, \`updateBucket\`, \`deduct\`, \`getLedger\`). \`UsageManagerConfig.store\` accepts \`UsageStore | UsageStoreFactory\` where \`UsageStoreFactory = (c: unknown) => UsageStore\`. <!-- lore:019caf12-49c0-73f8-86a4-0634fbe887e9 -->
* **hono-openapi requestBody.required generation in getSpec()**: In \`src/handler.ts\`, the \`getSpec()\` function builds \`requestBody\` for \`json\` and \`form\` validator targets. There are two branches: 1. \*\*Creating new requestBody\*\* (when \`docs.requestBody\` doesn't exist or has no content) — this is where \`required: true\` should be set (fixed in PR #223) 2. \*\*Appending to existing requestBody\*\* (else branch) — only adds media content, doesn't touch \`required\` since the object already exists (possibly from \`defaultOptions\`) Per OpenAPI 3.1, \`requestBody.required\` defaults to \`false\`, so it must be explicitly set to \`true\`. Using \`validator('json', schema)\` or \`validator('form', schema)\` inherently means the body is required — if a user wanted optional, they'd use \`describeRoute\` with manual \`requestBody\` config. The fix affects all vendors uniformly since the code path is shared in \`handler.ts\`, not per-vendor.

<!-- lore:019caee4-adca-7417-9656-d0cff25719de -->
* **hono-openapi resolver() option passing has two different nesting levels**: In hono-openapi's \`resolver()\` function (\`src/middlewares.ts\`), the \`userDefinedOptions\` parameter flows to two conversion functions with different nesting expectations: 1. \*\*\`toJsonSchema(schema, options)\`\*\* from \`@standard-community/standard-json\` — expects flat options like \`{ fallback: ... }\` 2. \*\*\`toOpenAPISchema(schema, context)\`\*\* from \`@standard-community/standard-openapi\` — expects \`{ components?, options?: { fallback: ... } }\` where the nested \`options\` object is what gets passed through to \`toJsonSchema\` internally via \`toJsonSchema(schema, context.options)\` Callers of \`resolver()\` also pass options at different levels: - \*\*\`validator()\`\*\* passes \`{ media?, options?: { ... } }\` (vendor options nested under \`options\`) - \*\*\`describeResponse()\`\*\* passes flat \`Record\<string, unknown>\` - \*\*Direct calls\*\* (e.g., in \`describeRoute\` responses) typically pass nothing When adding vendor-specific defaults (like ArkType's morph fallback), you must be careful to only inject into the \`toOpenAPISchema\` path's nested \`options\` object, and leave the \`toJSONSchema\` path's flat options unchanged. Changing \`toJSONSchema\` option assembly affects all vendors.

### Gotcha

<!-- lore:019caf24-0b27-7fbb-8206-c853f62f4dd0 -->
* **Always branch from main when creating fix branches to avoid carrying unrelated commits**: When creating a new fix branch (e.g. \`fix/issue-196-...\`), always branch from \`main\` (or \`origin/main\`), not from a previous fix branch. If you branch from another fix branch that later gets merged/squashed into main, the new branch will carry the old commit with a different hash than what landed in main. This requires a rebase onto \`origin/main\` + force push to clean up. Fix if it happens: \`git rebase origin/main\` — git auto-skips previously applied (cherry-picked/squashed) commits. Then \`git push --force-with-lease\` to update the remote branch.

<!-- lore:019f07d4-ba55-7f42-bb22-c92f418c780d -->
* **GitHub Actions setup-node cache:pnpm fails without cache-dependency-path**: Trap: \`actions/setup-node@v4\` with \`cache: 'pnpm'\` looks complete but fails at post-job cleanup with 'Path Validation Error: Path(s) specified in the action for caching do(es) not exist'. Two distinct root causes: (1) Missing \`cache-dependency-path: pnpm-lock.yaml\` — always add this alongside \`cache: 'pnpm'\`. (2) \`pnpm install\` never runs in the job — if no pnpm store directory is created, there's nothing to cache and cleanup fails. Fix: either add \`pnpm install\` to the job, or remove \`cache: 'pnpm'\` and \`cache-dependency-path\` entirely from jobs that don't install dependencies (e.g. \`release.yml\`, \`publish.yml\`). In hono-usage-limiter, \`release.yml\` and \`publish.yml\` don't run \`pnpm install\` — cache config was removed from both.

<!-- lore:019f07d4-ba59-7ead-85f7-e555bd3426be -->
* **hono-usage-limiter publish.yml needs actions:read permission for gh run list**: Trap: \`gh run list --workflow 'Package Artifacts' --branch 'release/x.y.z'\` in \`publish.yml\` returns HTTP 403 'Resource not accessible by integration' — looks like a branch or workflow name issue. Fix: the GITHUB\_TOKEN lacks \`actions: read\` permission. Add \`permissions: actions: read\` to the publish workflow job. In hono-usage-limiter run 28281468836, this caused 'Wait for package artifacts on release branch' to fail, blocking the publish step entirely.

<!-- lore:019f07ae-b9eb-7e7c-b3ed-2264ab17d0ee -->
* **hono-usage-limiter: totalConsumed JSDoc says 'lifetime' but resets on window/refill/provision**: Trap: \`UsageBucket.totalConsumed\` JSDoc (src/types.ts) says 'lifetime of this bucket', implying it accumulates forever. Fix: \`reset()\`, auto-refill (\`resolveBucket()\`), and \`provision()\` all set \`totalConsumed: 0\` — actual semantics are 'current window'. \`UsageBalanceInfo.totalConsumed\` JSDoc correctly says 'current window'. The \`UsageBucket\` JSDoc is misleading and should be corrected before publish.

<!-- lore:019f033c-4bd4-7d47-83d4-bd15de15ebf4 -->
* **MemoryStore getLedger: sort by insertion index, not timestamp**: Trap: sorting ledger entries by \`created\_at\` timestamp (Date.now()) looks correct for newest-first ordering. Fix: entries created in rapid succession (e.g. in tests) get identical timestamps, making the sort unstable and tests flaky. \`MemoryStore.getLedger\` must sort by reversed insertion index instead of timestamp. Confirmed bug in \`src/memory.ts\` caught by test \`MemoryStore > should return ledger entries newest first\`. Note: class is now \`MemoryStore\` implementing \`UsageStore\` (renamed from \`CreditStore\`).

<!-- lore:019f07ae-b9e9-75e0-9929-c4d70f31d7bf -->
* **MemoryStore.getBucket returns mutable reference — silent state corruption**: Trap: \`MemoryStore.getBucket()\` (memory.ts) returns the actual object stored in the internal Map, which looks fine since it's typed as \`UsageBucket\`. Fix: consumer mutation (e.g. modifying returned bucket fields) silently corrupts store state because it's the same reference. Fix by returning \`{ ...bucket }\` spread. This is a pre-publish bug in hono-usage-limiter v0.1.0.

<!-- lore:019f0920-b562-781d-83e6-44f929072025 -->
* **Named function expression inside same-named outer function gets numeric suffix**: Trap: using a named function expression \`async function describeRoute(\_c, next) { ... }\` inside the outer \`describeRoute()\` function looks like it should set \`.name\` to \`'describeRoute'\`. Fix: JavaScript auto-suffixes the inner name to \`'describeRoute2'\` to avoid shadowing the outer function. Use \`Object.defineProperty(middleware, 'name', { value: 'describeRoute', configurable: true })\` instead — this bypasses the naming collision entirely. Applies to any helper function that creates a middleware with the same name as its enclosing function.

<!-- lore:019f079e-b492-75a2-98bb-9cf427bde55c -->
* **pkg-pr-new requires GitHub App installation — 404 on /check is not a code error**: Trap: \`pnpm exec pkg-pr-new publish "."\` failing with \`{"statusCode":404,"message":"There is no workflow defined for ..."}\` looks like a misconfigured workflow or wrong publish path. Fix: the pkg-pr-new GitHub App must be explicitly installed on the repo at https://github.com/apps/pkg-pr-new — it's not inherited from org-level installs. No code change needed. In hono-usage-limiter, the 'Release preview' CI workflow fails for this reason while 'CI Tests' passes fine.

### Pattern

<!-- lore:019caf8e-1b12-7ea5-a7ec-d4b7570caf58 -->
* **hono-openapi release process: version bump, commit, tag, push**: To release a new version of hono-openapi: 1. Update \`version\` in \`package.json\` 2. Commit with message \`released v{X.Y.Z}\` (matching the most recent convention — earlier releases used \`release v{X.Y.Z}\` but recent ones use \`released\`) 3. Create git tag \`v{X.Y.Z}\` 4. Push both commit and tag: \`git push origin main --tags\` Tag naming convention: \`v{X.Y.Z}\` (e.g. \`v1.3.0\`). Older pre-1.0 tags used \`core@{X.Y.Z}\` format but that's no longer used.

<!-- lore:019caf20-58f2-7228-b85d-b9dcc9e18aef -->
* **hono-openapi vendor-specific auto-injection pattern in resolver()**: hono-openapi's \`resolver()\` function uses a vendor detection + injection pattern to auto-fix known vendor limitations. The pattern: 1. Detect vendor via \`schema\["~standard"].vendor\` (e.g. \`"zod"\`, \`"arktype"\`) 2. For the \`toOpenAPISchema\` path, inject vendor-specific defaults into the nested \`options\` object 3. Preserve user-provided options — if the user already supplied the relevant option (e.g. \`override\`, \`fallback\`), don't replace it 4. Further refine detection with schema-level checks (e.g. \`"\_zod" in schema\` for Zod v4 vs v3) Current auto-injections: - \*\*ArkType\*\* (\`injectArktypeFallback\`): Injects \`{ options: { fallback: (ctx) => ctx.base } }\` to handle morph schemas (PR #222) - \*\*Zod v4\*\* (\`injectZodV4DateOverride\`): Injects \`{ options: { unrepresentable: "any", override: zodV4DateOverride } }\` to handle \`z.date()\` (PR #224) Both follow the same structure: a private helper function that checks user options at both flat and nested levels, returns \`{ options: { ... } }\` or \`undefined\`, and gets spread into the \`toOpenAPISchema\` context.

<!-- lore:019f0920-b567-7915-8233-54b4bbd667af -->
* **hono-openapi: naming middleware functions for observability via Object.defineProperty**: Both \`describeRoute()\` and \`validator()\` in \`src/middlewares.ts\` use \`Object.defineProperty(middleware, 'name', { value: '\<name>', configurable: true })\` to set meaningful function names. Named function expressions are rejected for this use case because a same-named inner function inside the outer helper gets a numeric suffix (e.g. \`describeRoute2\`). The \`configurable: true\` flag is required so downstream code (e.g. Sentry's \`@sentry/hono\`) can read and display the name in spans. Applied in PR fixing issue #231.

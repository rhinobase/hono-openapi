### Architecture

<!-- lore:019fd5b3-072e-7b9a-ba84-26e46539417f -->
* **Freestyle Cloud usage-limiter: org-member-scoped + CachedUsageStore wrapper**: Freestyle Cloud's usage tracking (apps/server) is always scoped to the active organization member (member ID), never directly to userId. \`resolveUsageOwner(db, userId, activeOrgId)\` resolves membership (active org first, else earliest membership as fallback across orgs), caching (user,org)→memberId for 1hr; every user has a guaranteed auto-created personal-workspace membership, so \`NoOrganizationError\` should be rare and is caught → HTTP 400 (never let it 500). \`CachedUsageStore\` wraps \`D1Store\` with a 2-min Cache API layer on \`getBucket()\` (raw D1 read is ~88ms) — but \`deduct()\` and \`getLedger()\` always bypass cache and hit D1 directly (D1 is atomic/authoritative: inner.deduct() runs first, then the cache entry is patched in-place, never invalidated) specifically to avoid overspending against a stale cached bucket. This is an intentional fail-open soft gate — an over-budget owner can slip through for up to the TTL within a single colo. Same owner-resolution helper (\`resolveUsageOwnerId\`) is shared between the HTTP middleware and the streaming SttSession Durable Object.

* **hono-openapi requestBody.required generation in getSpec()**: In \`src/handler.ts\`, the \`getSpec()\` function builds \`requestBody\` for \`json\` and \`form\` validator targets. There are two branches: 1. \*\*Creating new requestBody\*\* (when \`docs.requestBody\` doesn't exist or has no content) — this is where \`required: true\` should be set (fixed in PR #223) 2. \*\*Appending to existing requestBody\*\* (else branch) — only adds media content, doesn't touch \`required\` since the object already exists (possibly from \`defaultOptions\`) Per OpenAPI 3.1, \`requestBody.required\` defaults to \`false\`, so it must be explicitly set to \`true\`. Using \`validator('json', schema)\` or \`validator('form', schema)\` inherently means the body is required — if a user wanted optional, they'd use \`describeRoute\` with manual \`requestBody\` config. The fix affects all vendors uniformly since the code path is shared in \`handler.ts\`, not per-vendor.

### Decision

<!-- lore:019fd59b-13dd-72e4-b782-6c046a7cb743 -->
* **hono-openapi PR #238: conditional OpenAPI 3.2 version bump for QUERY method**: PR #238 unconditionally bumps emitted \`openapi\` field from "3.1.0" to "3.2.0" to support HTTP QUERY method's dedicated \`query\` Path Item field (3.2-only; absent in 3.1, so 3.1 validators reject it). Verified via official migration guide (learn.openapis.org/upgrading/v3.1-to-v3.2.html): 3.2 is fully backward-compatible with 3.1 at document-structure level, no breaking changes overall. Recommended fix: "conditional versioning" — emit 3.2.0 only when a route actually uses a 3.2-only construct (query op or additionalOperations), else keep 3.1.0. Rejected the blanket bump because it silently breaks downstream tooling pinned to 3.1.x for users who never use QUERY. Also flagged DRY gap: version string duplicated across handler.ts + 8 snapshot files with no single OPENAPI\_VERSION constant. Core fix (ALLOWED\_METHODS += "QUERY", @ts-expect-error removal) is correct and mergeable independent of the version bump.

* **Always branch from main when creating fix branches to avoid carrying unrelated commits**: When creating a new fix branch (e.g. \`fix/issue-196-...\`), always branch from \`main\` (or \`origin/main\`), not from a previous fix branch. If you branch from another fix branch that later gets merged/squashed into main, the new branch will carry the old commit with a different hash than what landed in main. * **hono-openapi getPathContext() regex substring bug — PR #225**: Trap: old \`getPathContext()\` (src/utils.ts) used \`path.match(key)\`, treating the context key as a regex and doing substring matching — looks correct because it works fine for exact paths, but silently matches unrelated routes sharing a trailing segment. * **hono-openapi PR #226 hasValidation heuristic false-positives on manual params/body**: Trap: \`hasValidation = schema.requestBody || (schema.parameters?.length > 0)\` (used to gate auto-injecting a 400 validation-error response) looks correct because validator-derived specs do populate parameters/requestBody. <!-- lore:019fd5b3-074e-7d5a-ac0e-8ac5913186eb -->
* **hono-usage-limiter deduct() result.success is always true — no atomic gating**: Trap: \`UsageDeductResult.success\` looks like it should reflect whether the account had sufficient balance, since \`deduct(amount, reason)\` returns a result object. Fix: both \`MemoryStore.deduct\` and \`D1Store.deduct\` do unconditional subtraction and hardcode \`success: true\` — it never checks or rejects insufficient balance, allowing negative \`usageRemaining\`. There is no atomic check-and-deduct (\`tryDeduct\`). Freestyle Cloud works around this by calling \`usage.check()\` as a soft gate before calling \`deduct()\` separately — this has a TOCTOU race under concurrency (two concurrent requests can both pass check() then both deduct). Recommended library fix: atomic \`tryDeduct()\` returning \`{success:false, remaining}\` on insufficient balance instead of unconditionally subtracting.

* **hono-openapi: naming middleware functions for observability via Object.defineProperty**: Both \`describeRoute()\` and \`validator()\` in \`src/middlewares.ts\` use \`Object.defineProperty(middleware, 'name', { value: '\<name>', configurable: true })\` to set meaningful function names. * **hono-usage-limiter known design gaps — P0-P3 priority list**: From reviewing real usage in Freestyle Cloud, ranked gaps for future hono-usage-limiter work: P0: atomic tryDeduct() (deduct().success is always true, no real gating — see deduct() gotcha entry); atomic window refill — \`resolveBucket()\` in manager.ts does read-then-write on expiry, races under concurrent requests in the same colo, can double-refill or clobber totalConsumed. P1: no built-in caching — every serious consumer hand-builds a CachedUsageStore (2-min Cache API layer, D1 always authoritative for deduct/getLedger); \`UsageStoreFactory\` is untyped \`(c: unknown) => UsageStore\`, forcing \`as Context\<Env>\` casts at every call site — should be generic over Hono Env. P2: \`defaultUsage\`/\`defaultWindowDurationMs\` ignored after first provision, requiring hand-written SQL migrations to change limits; no bulk/admin operations — admin analytics bypass the lib entirely via raw SQL against usage\_buckets/usage\_ledger. P3: getLedger has no limit clamp; UnstorageStore.updateBucket is O(n) scan (needs id→ownerId reverse index like the ledger); reason field is an untyped free string; no credit()/refund path (deduct requires positive amount only).

<!-- lore:019fd5b6-e7ba-7b6c-95fe-802c8d062f1f -->
* **VALIDATION\_MARKER: enumerable string key survives mergeSpecs, symbols don't**: hono-openapi's \`mergeSpecs\` (src/utils.ts) rebuilds spec objects via \`Object.entries(spec)\`-based reduce, which silently drops symbol keys and non-enumerable properties. To reliably tag validator-derived specs (so downstream code like \`removeExcludedPaths\` can distinguish real \`validator()\` usage from manually-documented \`describeRoute\` params/body), use an enumerable STRING key marker (e.g. \`VALIDATION\_MARKER = "\_\_HonoOpenAPIValidator\_\_"\` set as \`docs\[VALIDATION\_MARKER] = true\` in \`getSpec\`'s validator branch), not a Symbol or non-enumerable property — those get silently stripped by the merge and the marker never reaches \`removeExcludedPaths\`. Boolean values propagate correctly through repeated \`mergeSpecs\` calls (else-branch direct assignment). Always \`delete schema\[VALIDATION\_MARKER]\` before emitting the final spec to avoid leaking it into output.
